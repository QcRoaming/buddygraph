# BuddyGraph 性能测试报告

测试日期：2026-11-05。本报告评估 BuddyGraph 图优化对编译耗时、CPU 执行耗时和临时内存分配的影响。所有对比使用同一份项目源码与同一台机器。

## 1. 测试目的与整体安排

本次测试回答三个问题：编译和启动一个模型需要多长时间？图优化能让实际计算快多少？优化前后的计算结果是否正确？

为此，测试分成两部分：

| 测试部分 | 使用什么输入 | 如何执行 | 主要观察什么 |
|---|---|---|---|
| 编译与启动测试 | 一个固定的微型 ONNX 模型 | 分别启动导入器、编译器和 `mlir-runner` | ONNX 导入、MLIR 编译和 runner 启动执行的耗时 |
| 稳态执行测试 | 六组运行时张量输入，覆盖逐元素链和卷积链 | 提前编译为共享库，在同一进程中重复调用 | 排除编译、加载和 JIT 后，一次计算需要多长时间 |

第一部分用于了解编译链的开销，第二部分用于判断图优化的计算收益。两部分的模型、执行方式和计时范围不同，结果分别比较。

测试顺序为：**构建并运行正确性回归 → 准备输入 → 生成各组优化版本 → 核对输出 → 采集性能数据 → 复测关闭/开启优化的差异**。

## 2. 对比方案：比较哪些优化

每个测试输入都生成以下五个版本。表格中简称与脚本参数的对应关系如下：

| 报告中的名称 | 脚本名称 | 启用的图优化 | 作用 |
|---|---|---|---|
| 关闭图优化 | `off` | 无 | 作为比较基准 |
| 仅规范化与 CSE | `canonicalize_cse` | Canonicalize、公共子表达式消除 | 简化表达式，消除重复计算 |
| 仅 BN 折叠 | `bn_folding` | Conv-BN folding | 将 BatchNorm 参数预先合入卷积权重与偏置 |
| 仅逐元素融合 | `elementwise_fusion` | Elementwise fusion | 将相邻逐元素运算合并，减少中间张量 |
| 全部图优化 | `all` | BN 折叠 → Canonicalize → CSE → 逐元素融合 | 观察组合后的收益 |

**“关闭图优化”只关闭上表的图优化。** 所有版本仍执行相同的 BGraph→Linalg→LLVM 转换；稳态执行测试也都使用相同的 LLVM `-O3` 后端。因此，对比反映的是这些图优化在同一后端上的增量收益。

所有版本使用相同输入数据、相同输出格式和相同计时方式。第一轮测试全部五组；第二轮针对六组稳态输入，重新编译并复测“关闭图优化”和“全部图优化”。

## 3. 测试输入

### 3.1 编译与启动测试：固定 ONNX 小模型

模型为 `elementwise_constant.onnx`，由项目的 [fixture 生成器](../../frontend/BGraph/generate_test_models.py) 产生。计算过程为：

```text
输入常量 → Conv → BatchNorm → Add → Relu → Mul → ReduceMean → 标量结果
```

| 项目 | 具体内容 |
|---|---|
| 数据类型 | 所有计算数据为 `float32` |
| 主输入 `a` | 形状 `[1,1,2,2]`，数值为 `[[[[-2,1],[3,5]]]]` |
| Conv | 1×1 卷积，权重为 1、偏置为 0，输入输出形状相同 |
| BatchNorm | 构造成保持输入数值的参数：mean=0、variance=1、bias=0、epsilon=1e-5、scale≈√(1+epsilon) |
| Add | 加上 `[1,2]`，沿最后一维广播 |
| Mul | 乘以标量 2 |
| 输出 | 对所有元素取平均，预期标量结果为 `7.0` |

该模型**没有运行时输入参数**，输入与权重都存储在 ONNX 常量中。它只有 4 个主输入元素，适合验证编译链、优化结构和启动开销。

### 3.2 稳态执行测试：六组较大张量

这部分直接构造 BGraph IR，函数接收运行时数组 `x`、`b`、`factor`，返回完整输出数组 `y`。运行时输入可以避免整个计算因输入全为常量而在编译阶段被预先算出。

测试三种计算链：

| 计算链 | 计算内容 | 用途 |
|---|---|---|
| Relu 链 | `y = max(x + b, 0) * factor` | 观察 Add→Relu→Mul 融合在不同张量大小上的效果 |
| Clamp 链 | `y = clip(x + b, -0.5, 0.75) * factor` | 观察另一种逐元素运算的融合效果 |
| 卷积链 | `y = Relu(BN(Conv(x)) + b) * factor` | 观察 BN 折叠与逐元素融合在含卷积的图中的效果 |

具体形状如下：

| 用例 | `x` 形状 | `b`、`factor` 和输出 `y` 的形状 |
|---|---|---|
| Relu 链，4,096 元素 | `[4096]` | `[4096]` |
| Relu 链，65,536 元素 | `[65536]` | `[65536]` |
| Relu 链，1,048,576 元素 | `[1048576]` | `[1048576]` |
| Clamp 链，1,048,576 元素 | `[1048576]` | `[1048576]` |
| 卷积链，16×16 | `[1,8,16,16]` | `[1,16,16,16]` |
| 卷积链，32×32 | `[1,8,32,32]` | `[1,16,32,32]` |

所有数组均为连续的 `float32` 数据。`x`、`b`、`factor` 分别从 `[-2,2)`、`[-0.5,0.5)`、`[0.25,1.75)` 均匀生成。

卷积使用 NCHW 布局、8 输入通道、16 输出通道、3×3 卷积核、stride=1、padding=1、groups=1。卷积权重形状为 `[16,8,3,3]`；权重、偏置和 BN 参数使用固定随机种子生成，作为图中的常量，允许 BN 折叠。

数值校验使用种子 11、22、33 的三组输入；计时使用种子 33 的输入。同一用例的各优化版本使用完全相同的数据。

### 4.1 环境

| 项目 | 配置 |
|---|---|

| 操作系统 | WSL2 Linux 6.18.54.1 |
| LLVM / MLIR | 21.1.8 |

CPU 频率未锁定，WSL 宿主机负载和调度可能造成耗时波动。

### 4.2 编译与启动如何计时

使用 [benchmark.py](../../scripts/benchmark.py)，分别测量以下阶段：

| 测量项 | 计时起止与包含的工作 | 采样次数 |
|---|---|---:|
| ONNX 导入 | 启动 Python 导入器，完成模型检查、形状推导和 BGraph IR 生成后退出 | 30 |
| 单个 pass 调用 | 启动 `buddygraph-opt`，解析 IR，执行指定 pass 后退出 | 每项 30 |
| 完整 MLIR 编译 | 启动 `buddygraph-opt`，完成指定图优化与 BGraph→LLVM dialect 转换后退出 | 每组 30 |
| runner 启动与执行 | 启动 `mlir-runner`，解析 LLVM dialect、JIT 编译并执行后退出 | 每组预热 5 次，再测 50 次 |

这些数字均为独立进程的实际经过时间。完整 MLIR 编译不包含 ONNX 导入与机器码生成；runner 则包含 JIT。各阶段独立采样，没有测量把所有阶段串在一起的一次总耗时。

### 4.3 稳态执行如何计时

使用 [benchmark_native.py](../../scripts/benchmark_native.py)，对每个用例执行：

1. 将五个版本分别编译成原生共享库，加载完成后再开始计时。
2. 用 NumPy 计算参考输出，逐元素校验各版本的输出。
3. 自动选择每批调用次数，使一批执行约 20 ms；再预热 5 批。
4. 采集 31 批数据，每轮随机打乱五个版本的执行顺序。
5. 将“批次耗时 ÷ 批内调用次数”作为该批的平均单次耗时，取 31 批的中位数作为主要结果。
6. 计时结束后再次校验输出；第二轮重新编译并复测关闭/开启全部图优化。

重复调用的循环在 C 中执行，避免每次调用都经过 Python。计时包含函数调用、计算、中间缓冲区的分配与释放、结果写入与输出拷贝；输入和输出缓冲区提前分配，编译、加载、JIT 和 NumPy 校验均在计时之外。

测试重复使用同一组输入与缓冲区，衡量的是预热后的连续执行。结果表中的 **median 是中位数**，越低越好；**加速比 = 关闭图优化耗时 ÷ 开启优化耗时**，越高越好。

### 5.4 优化后的中间表示与分配变化

这一节做的是**编译期结构统计**，用于检查图优化是否减少了独立的计算和中间缓冲区。第 5.1 节的计时回答“快了多少”，这里的统计帮助解释“程序结构发生了什么变化，为什么可能变快”。例如，融合是否真正消除了中间张量，而不只是改变了图上的算子名称。

不同指标选取不同的统计位置：

| 指标 | 本次脚本中的统计位置 | 观察目的 |
|---|---|---|
| 小模型的 `linalg.generic` 数量 | BGraph→Linalg 转换后、缓冲化前的 IR | 观察还剩多少个独立的 Linalg 计算操作 |
| `memref.alloc` 数量与静态分配总量 | 缓冲化后的 IR | 观察该阶段显式创建了多少个缓冲区，以及它们的大小 |

**分配指标选在缓冲化后，是因为此时存储安排才被显式表达出来。** 缓冲化前，`tensor` 表示计算得到的值；一个 tensor 结果并不必然需要单独分配内存，也可能复用已有缓冲区。缓冲化把 tensor 计算转换为对 `memref` 缓冲区的读写，显式产生分配、复制等操作。此时统计 `memref.alloc`，比直接按图算子数或 tensor 结果数估算内存更有依据。

这个阶段仍保留 `memref<1048576xf32>` 这样的形状与类型，容易计算分配大小，并能追溯到图优化的变化。继续降到 LLVM 后，类型会转换为指针和描述符，后端也可能继续消除或改写分配；本表选择统一的缓冲化阶段作结构对照。

以本次百万元素 Relu 链为例，实际生成的缓冲化 IR 对应以下过程：

```text
未融合：t1 = Add(x, b)           → 一个 N 元素缓冲区
        t2 = Relu(t1)            → 一个 N 元素缓冲区
        t3 = Mul(t2, factor)     → 一个 N 元素缓冲区
        将 t3 复制到调用方的输出缓冲区

融合后：t[i] = max(x[i] + b[i], 0) * factor[i]
                               → 只需一个 N 元素结果缓冲区
        将 t 复制到调用方的输出缓冲区
```

其中 `N = 1,048,576`，每个 f32 为 4 字节，所以每个缓冲区为 4 MiB，三个缓冲区合计 12 MiB。表中的 12→4 MiB 就来自这类显式分配的减少。

| 用例与指标 | 关闭图优化 | 全部图优化 |
|---|---:|---:|
| 固定 ONNX 小模型：`linalg.generic` 数量 | 7 | 4 |
| 固定 ONNX 小模型：`alloc` 数量 | 7 | 4 |
| 固定 ONNX 小模型：临时缓冲区分配总量 | 88 B | 40 B |
| 百万元素逐元素链：`alloc` 数量 | 3 | 1 |
| 百万元素逐元素链：临时缓冲区分配总量 | 12 MiB | 4 MiB |
| 32×32 卷积链：`alloc` 数量 | 6 | 3 |
| 32×32 卷积链：临时缓冲区分配总量 | 364,672 B | 168,064 B |

“分配总量”是该阶段所有静态 f32 `memref.alloc` 的字节数之和，不考虑缓冲区生命周期是否重叠，也不等于运行时峰值内存或进程 RSS。调用方预先分配的输入/输出、常量存储和分配器开销不计入；函数内部用于暂存最终结果的 `alloc` 仍计入，如上例的 t3 和 t。`linalg.generic` 数量也不等于最终机器代码的循环数量。

这些指标支持“图优化减少了该阶段的计算操作和显式缓冲区”这一结论。减少了多少实际内存流量、最终占用多少内存、是否获得加速，仍需分别结合硬件计数器、运行时内存测量和执行计时判断。

## 6. 结果分析

### 6.1 逐元素链的主要收益来自融合

在百万元素 Relu 链上，仅开启逐元素融合就将耗时从 2055.47 µs 降到 1047.37 µs，加速 1.96×、耗时减少 49.0%。Clamp 链也有类似结果：1785.33 µs 降到 919.98 µs，加速 1.94×。

这里每个元素只需要做一次加法、一次激活和一次乘法，算术工作量很小。未融合时，三段计算之间通过完整数组传递结果：先把 Add 的结果写入缓冲区，再由 Relu 读出；Relu 的结果又要写入另一个缓冲区，再由 Mul 读出。融合后，在同一次循环迭代中连续完成三个运算，两份中间数组的读写被消除。

**融合没有减少加法、激活和乘法的语义计算次数，主要减少的是中间数据的读写、缓冲区分配与释放，以及独立遍历。** 本例 IR 中的三个逐元素计算合为一个，缓冲区从 3 个降到 1 个，分配总量从 12 MiB 降到 4 MiB。这些变化覆盖了这条短链的大部分执行过程，因此对总耗时影响明显。

按图中数组的逻辑读写次数估算，三段计算合计访问 `32N` 字节，融合后为 `16N` 字节；本次测量入口还保留双方共有的输出拷贝，另计 `8N` 字节。这里 `N` 是元素数，每个 f32 为 4 字节。这是解释读写减少的模型，不是实测 DRAM 流量，也不是精确的加速比预测；缓存、分配器、循环代码和 CPU 调度都会影响最终耗时。

仅规范化/CSE 和仅 BN 折叠对这些逐元素输入没有显示稳定收益。逐元素链本身没有 Conv-BN 模式，因此不能期待 BN 折叠改善它们。

### 6.2 卷积链有收益，但幅度明显小于逐元素链

先在**同一条 32×32 卷积链**中比较两种优化。以下均为第一轮中位数，基准为 367.52 µs：

| 启用的优化 | 执行耗时（µs） | 相对基准的耗时降幅 | IR 中的缓冲区数量 |
|---|---:|---:|---:|
| 关闭图优化 | 367.52 | — | 6 |
| 仅 BN 折叠 | 354.30 | 3.60% | 5 |
| 仅逐元素融合 | 360.58 | 1.89% | 4 |
| 全部图优化 | 349.29 | 4.96% | 3 |

逐元素融合在这条卷积链中也只有小幅收益，而且低于单独 BN 折叠。因此，主要差别是**被消除的开销占整条计算链的比例不同**，不能把纯逐元素链约 2× 的加速，直接当成逐元素融合在任何图中的固定收益。

**第一，BN 折叠消除了 BN，但保留了卷积的计算量。** 对推理阶段的固定 BN 参数，可以按通道预先计算：

```text
alpha = gamma / sqrt(variance + epsilon)
新卷积权重 = alpha * 原卷积权重
新卷积偏置 = beta + alpha * (原卷积偏置 - mean)
```

随后用新权重和偏置执行卷积即可。当前实现见 [FoldBatchNorm.cpp](../../lib/BuddyGraph/Transforms/FoldBatchNorm.cpp)。它没有减少输入通道、输出通道或卷积核大小，因此没有减少卷积的乘加次数。

本次 32×32 用例有 `1×16×32×32 = 16,384` 个输出元素，每个输出元素要累加 `8×3×3 = 72` 项，合计 **1,179,648 次乘加**。BN 只在每个输出元素上执行归一化，规模小得多。IR 中卷积操作在折叠前后都保留；单独 BN 折叠使 `linalg.generic` 从 5 个降到 4 个、缓冲区从 6 个降到 5 个，少掉一个 64 KiB 的 BN 结果缓冲区。报告中 6→3 的变化则属于“全部图优化”，包含逐元素融合的贡献。

**第二，未折叠版本已经受益于公共 LLVM 后端优化。** 在保存的 [未折叠 LLVM IR](performance-data/performance-2026-11-05/native/conv_bn_32/off/kernel.opt.ll) 中，`sqrt(variance + epsilon)` 已被移到通道循环内、空间循环外。该用例每个通道计算一次开方，再供该通道的 32×32 个元素使用；不能按 16,384 次开方来估计 BN 折叠的额外收益。逐元素的减、除、乘、加仍保留，折叠可以进一步消除它们。

**第三，被省掉的工作只占总耗时的一部分。** 整条链还包含 padding、卷积、Add→Relu→Mul、输出拷贝和其余缓冲区管理。这符合 Amdahl 定律：若某部分只占总耗时的 4%，即使完全消除它，总加速也只有 `1 / (1 - 0.04) ≈ 1.042×`。这里的 4% 是用于说明关系的例子；本次没有单独计时 BN。367.52→354.30 µs 的差值约 13.22 µs，是整条链的净变化，也可能包含缓存和后端代码变化的影响。

两组输入的数据规模也不同：百万元素逐元素链的每个缓冲区为 4 MiB，而 32×32 卷积链的 BN 输出缓冲区只有 64 KiB。融合消除的绝对读写量与缓存条件不同，进一步限制了跨用例直接比较加速比的意义。

本次数据与代码结构共同支持以下解释：纯逐元素链省掉了占比较大的中间数据处理，卷积链的图优化省掉了卷积周围的一部分开销。尚未采集算子级时间和硬件计数器，因此不把“受 DRAM 带宽限制”或“卷积占比恰好为某个百分数”作为已验证结论。下一步可在相同输出形状下改变卷积核大小、输入通道数，并配合分阶段计时，检查卷积占比变化时 BN 折叠收益如何变化。

### 6.3 编译与启动耗时应和稳态执行分开理解

固定小模型的主输入只有 4 个元素，但 runner 仍需约 28–31 ms 才能完成一次启动执行；这个数字包含进程启动、IR 解析和 JIT，不能作为张量计算本身的耗时。

本次测得 ONNX 导入约 163 ms，完整 MLIR 编译约 22–24 ms。对于频繁启动的小任务，复用编译结果和执行进程值得关注；对于已经编译好、连续执行的任务，应以第 5.1 节的稳态结果评估图优化收益。

### 6.4 结论的适用范围

两轮复测支持：**在本次单线程合成负载上，逐元素链加速约 1.6–2.0×；卷积链加速约 1.04–1.06×；所有输出校验通过。**

测试使用固定形状、固定线程数和重复输入，尚未覆盖真实网络、不同模型的数据分布、多线程扩展或 GPU，也没有与 ONNX Runtime 等外部引擎比较。WSL 调度和 CPU 频率变化会影响绝对耗时，小幅差异不应单独视为稳定收益。

## 7. 复现方法

在仓库根目录运行。其他机器请将逻辑 CPU 编号 2 替换为可用编号，并避免同时运行其他重负载任务。

source scripts/env.sh

## 8. 2026-11-06：输出直写与卷积 CPU 调度扩展

本轮实现两项核心扩展，代码集中在 [CPUTransforms.cpp](../../lib/BuddyGraph/Transforms/CPUTransforms.cpp)：

| 入口 | 实现内容 |
|---|---|
| `--bgraph-bufferize` | 内联计算函数，通过空张量消除将调用方输出传给 Linalg 的 destination，再执行 One-Shot Bufferization 和临时缓冲区释放 |
| `--bgraph-vectorize-conv` | 对缓冲化后的 NCHW Conv 按输出通道分块、沿输出宽度向量化；同一个输入向量供多个输出通道复用 |

输出直写复用 MLIR 的 destination 分析；本轮还补上驱动缺失的 func 内联接口注册。卷积调度默认 `vector-width=8 channel-tile=4`，使用向量 SSA 值保存一块输出的累加结果，保留原来的 `ic→kh→kw` 归约顺序和独立乘、加操作。宽度尾部用标量循环处理，输出通道尾部生成剩余通道的累加器。

当前向量路径处理静态 f32、NCHW、宽度方向 stride=1 且输入/输出最内层连续的 Conv；padding 已由已有 lowering 处理，dilation 参与索引计算。其他情况保留原有 Linalg 路径。输出直写入口沿用 `restrict writable` 的缓冲区契约。

### 8.1 如何隔离两项扩展的收益

原生 benchmark 增加两组配置，与现有 `all` 在同一版本中比较：

| 配置 | 图优化 | 输出与内存处理 | 卷积调度 |
|---|---|---|---|
| `all` | 全部 | 普通缓冲化，结果经临时缓冲区拷贝到输出 | 原有标准 lowering |
| `direct_output` | 全部 | 输出直写 | 原有标准 lowering |
| `cpu` | 全部 | 输出直写 | 通道分块与宽度向量化 |

三组都使用已接通的函数内联，因此用 `all→direct_output` 判断输出直写收益，用 `direct_output→cpu` 判断卷积调度收益。下面是新版本内部的对照，不与前文旧版本的绝对耗时混合归因。机器、单线程/CPU 2、预热和采样方法与前述稳态测试相同。

### 8.2 实测结果

第一轮中位数，单位 **µs/次**；默认调度参数为 `8×4`。

| 用例 | `all` | `direct_output` | `cpu` |
|---|---:|---:|---:|
| Relu 链，4,096 元素 | 2.43 | 2.26 | 2.27 |
| Relu 链，65,536 元素 | 42.40 | 37.43 | 37.87 |
| Relu 链，1,048,576 元素 | 1014.07 | 754.63 | 716.12 |
| Clamp 链，1,048,576 元素 | 953.48 | 630.67 | 615.70 |
| 卷积链，16×16 | 82.83 | 82.82 | 22.20 |
| 卷积链，32×32 | 338.28 | 333.32 | 87.13 |

输出直写使逐元素链在缓冲化 IR 中的额外分配从 **1 个降到 0 个**，输出拷贝从 **1 次降到 0 次**。百万元素 Relu 链的额外 4 MiB 结果缓冲区和对应拷贝被消除，两轮 `all→direct_output` 加速分别为 **1.34×、1.45×**；Clamp 链分别为 **1.51×、1.42×**。

卷积链中，输出直写消除的是最终逐元素结果的临时缓冲区；padding 和卷积结果缓冲区仍保留。32×32 用例的分配总量从 168,064 B 降至 102,528 B。卷积调度进一步改变主要计算的执行方式：16×16 用例两轮 `direct_output→cpu` 加速为 **3.73×、3.68×**，32×32 为 **3.83×、3.84×**。目标文件中已确认生成 `mulps`、`addps` 等 SIMD 指令。

逐元素用例没有 Conv，`cpu` 配置不会额外进行卷积优化；其与 `direct_output` 的小幅耗时差异不能算作卷积调度收益。例如百万元素 Relu 链两组优化后的 LLVM IR 除 ModuleID 路径外完全相同。

另测 `vector-width=4 channel-tile=2`，16×16、32×32 卷积链分别为 **25.62 µs、100.28 µs**。这提供了第二组参数对照；当前实现使用显式参数配置调度。
